# Results

Figures for the reference date 2026-09-28. All figures below come from synthetic data: the
legacy source was generated by `legacy_db/seed/generate_legacy_data.py` with its default fixed
seed (42) and reference date, and Synthea v4.0.0 was run with seed 42 (population 500) and the
same reference date. They describe how the pipeline behaves on that data, not the performance of
any real payer. Running the Quickstart commands produces them again, apart from load times and
CDC latency; see the reproducibility note at the end of this page.

In Phase 3 the generator changed: claims now fall inside the member's coverage, except for the
injected claims outside eligibility. This changed the random sequence, so the claim and prior
authorization figures differ from the ones published in Phase 1 (see the git history).

When the generators were pinned (see Reproducibility), the Synthea figures changed: the earlier
ones came from Synthea's continuous build, simulated up to the moment it ran, and could not be
produced again. The expedited mean decision time also moved from 30.8 h to 30.7 h. That change
came from a measurement error, not from the data: the model counted minute boundaries crossed
(`date_diff('minute', ...)`) instead of elapsed time, so the figure depended on the seconds of each
timestamp, and anchoring the legacy timestamps to midnight of the reference date shifted them.
The model now measures elapsed time, and the expedited mean is 30.8 h again (30.76 h; with the
old calculation, 30.75 h). No other prior authorization figure changed.

In Phase 6 the legacy generator gained the claim fields the CARIN Blue Button profiles require
(network status, type of bill, revenue codes, place of service, NDC and dispensing details) and
valid NPI check digits. The new fields come from a separate random generator, and the NPI draw
only has its last digit replaced, so every figure on this page stayed the same.

Phase 7 added the PBM feed and identity resolution. The PBM generator has its own random
generator and reads the legacy members without changing them, so the earlier figures stayed the
same; the FHIR totals grew by the PBM claims and pharmacies, reported separately below. After
v2.0.0, the PBM generator added duplicate cardholder IDs (from yet another random generator, so
the rest of the feed did not change), which moved the identity figures, and the legacy generator
replaced the ICD-10-CM code M54.5 with M54.50 on claims from October 2021 (see Terminology). The
replacement draws no random number, so no other figure changed. The cleanup of warnings that
followed changed the deduplication model (its m now comes from the linkage) and with it the
dedupe and review figures, added Synthea's provider files to the bronze loads, and added
narratives and plan type codes to the FHIR resources; the linkage, terminology, parity and other
figures did not change.

For the FHIR API, the legacy generator moved the 483 prior authorizations it had dated outside
the member's coverage (it draws the member and the date independently, as it once did for claims)
to a day inside it, at the same time of day and with the same delay to the decision, and gave
every request an amount. Both come from a separate random generator: every other legacy table came
out identical, value by value, and the prior authorization timeliness figures below did not
change.

The Provider Access API added a legacy table of opt-outs (`mbr_cnsnt`), generated from its own
random generator: the other seven legacy tables came out identical to the previous generator's,
value by value (compared by a hash of each table), so no earlier figure changed.

The move to DuckLake changed no figure on this page apart from load times: a full build on it
reproduced the view parity, terminology, identity, deduplication and timeliness figures. The
Splink scores changed in their last digits, because their input is now sorted (see
Reproducibility); every link, merge and review decision stayed the same.

## Data quality

From `gold.dq_issue_summary`. Member checks run on the deduplicated member table (5,000 members
from 5,094 source rows).

| Check                        | Detected | Population      | Detected % | Injection rate in generator |
|------------------------------|---------:|-----------------|-----------:|-----------------------------|
| Duplicate member IDs         |       94 | 5,000 members   |      1.88% | 1.5% of members             |
| Invalid gender code          |       51 | 5,000 members   |      1.02% | 1.0% of members             |
| Unparseable birth date       |       44 | 5,000 members   |      0.88% | 1.0% of members             |
| Claims with unknown member   |      242 | 25,000 claims   |      0.97% | 1.0% of claims              |
| Paid amount exceeds charged  |      405 | 25,000 claims   |      1.62% | 2.0% of paid claims         |
| Claims outside eligibility   |      251 | 24,758 claims   |      1.01% | 1.0% of claims              |
| Orphan claim lines           |      312 | 62,795 lines    |      0.50% | 0.5% of lines               |

Injection rates are probabilities, so observed counts differ from the nominal rate by random
variation. The paid-exceeds-charged rate applies only to paid claims: 405 of 20,173 paid
claims (2.01%). The outside-eligibility check applies only to claims whose member exists
(24,758), because claims with an unknown member have no coverage to compare with.

**Traceability of injected issues.** For two checks, the injected records can be identified
in bronze independently of the dbt models, because the generator assigns them IDs outside the
valid ranges:

- *Orphan claim lines:* the generator adds `int(62,483 × 0.005) = 312` lines whose claim IDs
  start with `C9`, which never matches a real header. The check flagged 312 lines, all 312 of
  them injected (312/312, no other lines flagged).
- *Claims with unknown member:* injected claims reference member IDs from `M900000000` up,
  while real members run from `M000000001` to `M000005000`. Bronze has 242 such claims (0.97%
  of 25,000, against a nominal 1.0%). The check flagged 242 claims, all 242 of them injected.

The other five checks have no independent ground truth in the data, so only their counts are
reported.

## Change data capture latency (Phase 2)

Run on 2026-09-28: a fresh snapshot, then `make cdc` (5-second polling) running while
`make changes` committed 300 events over 60 seconds. From `gold.cdc_latency`; latency is the time
between the commit in Postgres and the arrival of the change in bronze.

| Table      | Changes | Inserts | Updates | Deletes | p50 latency | p95 latency | Max latency |
|------------|--------:|--------:|--------:|--------:|------------:|------------:|------------:|
| `clm_ln`   |     340 |     189 |     117 |      34 |      2.06 s |      4.86 s |      5.05 s |
| `clm_hdr`  |     143 |      76 |      53 |      14 |      2.13 s |      4.86 s |      5.05 s |

| `mbr_mstr` |      36 |       0 |      36 |       0 |      2.86 s |      4.53 s |      4.86 s |

Across all 640 changes the median latency was 2.16 s and the maximum 5.05 s, which is what a
5-second polling interval implies: latency here is set by the polling interval, not by processing

with an average write time of 0.03 s. After the run, the current state rebuilt from the change
tables matched the Postgres tables row for row in all seven tables.

Both processes ran on the same machine, so the source and lakehouse clocks agree; with separate
hosts, clock skew would add to the measured latency.

## Incremental current state on DuckLake

Run on 2026-11-10. The current state of each legacy table is `silver.cdc_current__<table>`,
maintained incrementally (see [architecture](architecture.md#change-data-capture)). Each case was
followed by an incremental `dbt build` of the seven tables, the parity test with a full rebuild
(`assert_cdc_current_state_matches_full`) and the reconciliation with Postgres
(`scripts/cdc_reconcile.py`):

| Case                                                    | Changes applied | Path            | Parity with full rebuild | Rows only on one side vs. Postgres |
|---------------------------------------------------------|----------------:|-----------------|--------------------------|-----------------------------------:|
| Simulated activity (300 events: 220 inserts, 149 updates, 56 deletes in `clm_ln`) | 725 | watermark | passed | 0 |
| New snapshot (as after a lost slot)                     |   whole history | rebuild         | passed                   |                                  0 |
| `TRUNCATE` and reload (`make seed` through CDC)         |         101,201 | rebuild         | passed                   |                                  0 |
| Nothing new                                             |               0 | watermark       | passed                   |                                  0 |
| `make cdc-check` (200 events), as in CI                  |  397 (20 deletes) | watermark     | passed                   |                                  0 |

The incremental build of the seven tables takes about 2 seconds. To check that both checks can
fail, one row of `cdc_current__pa_req` was deleted and one amount in `cdc_current__clm_hdr`
changed: the parity test failed with 2 rows and the reconciliation reported both tables; a
`--full-refresh` restored them.

**Concurrent writers.** With the loader polling every 2 seconds (`make cdc`) and the activity
simulator committing 300 events over 60 seconds, a full `dbt build` (263 nodes) ran at the same
time. The loader applied 626 changes in 133 batches during the build, with no rejected commit;
latency from the Postgres commit to bronze was 0.42 s at the median, 1.28 s at the 95th percentile
and 2.77 s at most. A final sync and incremental build matched Postgres row for row. On the DuckDB
file, the loader had to back off while dbt held the file. That run also found a gap in the parity
test: it compared the incremental tables with a rebuild from change tables the loader had already
moved past, and failed; it now stops at the incremental table's watermark.

## Replication slot monitoring

Run on 2026-11-10 with `make slot-drill` (written to `data/slot_drill.json`), after `make ingest`.
With the loader stopped, the drill writes WAL one 16 MB segment at a time until Postgres
invalidates the slot, and checks each stage with `make slot-check`:

| Stage                         | Segments written | WAL retained | WAL pending | `wal_status` | `slot-check` |
|-------------------------------|-----------------:|-------------:|------------:|--------------|--------------|
| Healthy slot                  |                0 |       0.0 MB |      0.0 MB | reserved     | passes       |
| Above the 512 MB threshold    |               33 |     514.7 MB |    514.7 MB | reserved     | fails        |
| Past the 1 GB cap, checkpoint |               72 |          n/a |  1,138.7 MB | lost         | fails        |
| After the next sync           |                — |       0.0 MB |      0.0 MB | reserved     | passes       |

The alert fired at about half the cap, while the slot was still usable: Postgres reported
512 MB left before the slot would be at risk (`safe_wal_size`). The next `sync` found the slot
lost, recorded it in `bronze._cdc_slot_status` and took a new snapshot (101,194 rows, the same
legacy data). `gold.cdc_slot_lag` then showed one loss, and its warning test fired as intended.
The whole drill took about 4 seconds, because `pg_switch_wal` moves to a new segment without
writing it full.

Writing WAL this way is a stand-in for a stalled loader; it does not measure how fast real
traffic would fill the slot. The thresholds (512 MB alert, 1 GB cap) are sized for this local
setup.

referenced resources are checked against their target profiles too.

Known warnings are listed in `summary.json` with their reason (`fhir/validate.py`,
`KNOWN_WARNINGS`), apply only to warnings, never to errors, and do not fail the run.

Two checks sit outside the validator:

- **References.** The validator does not report a reference it cannot resolve inside a Bundle as
  an error (a Bundle with the provider Organization removed passed). A dbt test
  (`assert_fhir_references_resolve`) checks that every reference in all exported resources
  resolves, and `validate.py` fails if a sampled resource references something not exported.
- **Terminology cache.** Without a terminology server (`make fhir-validate`), the validator
  reports the NCPDP dispense as written code as an error, because the code system is distributed
  only as a stub; those errors are counted as not verifiable too. Every run clears the validator's
  terminology cache (`-clear-tx-cache`), because it otherwise reuses answers cached by earlier
  runs, and the result would depend on the machine. A test run against tx.fhir.org in Phase 6
  rejected the fictitious NDCs the generator first used, so it now uses 10 real NDCs of common
  generic drugs.

To check that the validation can fail, it was run on altered Bundles: removing the unique claim ID
type from an EOB and removing `meta.lastUpdated` from the payer Organization each produced errors
(the latter also on the EOB and Coverage that reference it).

**Terminology** (`gold.terminology_code_check`, every code in every exported
ExplanationOfBenefit, not a sample). `ingestion/load_terminology.py` loads the CMS ICD-10-CM
releases for FY2021 to FY2026 (code descriptions in tabular order, pinned by URL and SHA-256) and
the FDA NDC Directory into bronze; the CMS place of service codes are a seed. The model reads the
codes through a ViewDefinition (`eob_codes`), so it checks what the API would serve, and checks
each code on its service date: an ICD-10-CM code must be billable in the release for that fiscal
year, and an NDC must be listed and marketed on that date.

None is invalid, and `assert_terminology_codes_valid` fails the build if one is. It did not start
that way. The legacy generator drew the diagnosis M54.5 (low back pain), a billable code until
FY2021 that became a category on October 1, 2021, split into M54.50, M54.51 and M54.59. Every
claim dates from FY2024 or later, so M54.5 was invalid on all of them; the generator now writes
M54.50 (unspecified) from that date, 6,079 diagnoses. To check that the model can fail, its
compiled SQL was run with four extra codes on a 2025 claim: M54.5 came out invalid (a category),
Z99.999 invalid (not in the release), NDC 00000000000 invalid (not in the directory) and place of
service 98 invalid.

The two checks disagreed on one point: tx.fhir.org reported all 10 NDCs as inactive, while the FDA
directory of 2026-11-10 lists every one of them with no marketing end date. Asked directly
(`$validate-code`), tx.fhir.org answers from an NDC version dated 2021-11-01: it marked as inactive
every NDC tried, including packages marketed since 1987 and still listed, and it does not know
packages first marketed after 2021. Its `$lookup` for NDC fails with an error of its own. So no
choice of NDC would remove the warning. The lakehouse follows the FDA, which publishes the code
system, and the validation counts the warning as known. The FDA publishes only its current directory, so the NDC check cannot be pinned: the
release date and SHA-256 of each load are recorded in `bronze.terminology_releases`, and a drug
removed from the directory would make older claims fail.

## Identity resolution (Phase 7)

**The PBM feed** (`make pbm`, `scripts/generate_pbm_feed.py`). A pharmacy benefit manager
administers the pharmacy benefit for part of the members and issues its own cardholder IDs; its
files do not carry the payer's member ID. The generator takes 60% of the covered legacy members and
varies each record independently at documented rates, then adds people the payer does not know:

| Variation (PBM record of a member)                  | Rate | Records |
|-----------------------------------------------------|-----:|--------:|
| First name replaced by a common nickname            | 8%   |     210 |

| Last name typo                                      | 4%   |     114 |
| Different last name                                 | 2%   |      63 |
| Birth date with day and month transposed            | 2% (when both are 12 or less) | 20 |
| Birth date mistyped (day or year's last digit)      | 2%   |      72 |
| Birth date missing                                  | 1%   |      29 |
| Different ZIP code (moved)                          | 15%  |     436 |
| Gender missing                                      | 3%   |      87 |
| Legacy birth date invalid (PBM has a valid one)     | from the legacy source | 22 |
| Legacy gender invalid                               | from the legacy source | 28 |

Of the 2,900 PBM records of members, 1,841 have no variation and 1,059 have at least one. The
feed also holds 232 unrelated people, 29 look-alikes with a member's name, ZIP code and gender but
a different birth date, and 14 "twins" with a member's last name, birth date and ZIP code but
another first name. Finally, 3% of the members and unrelated people (94: 91 members, 3 unrelated)
hold a second cardholder ID, as when a PBM reissues a card after re-enrollment. The duplicate
record starts from the first one and is keyed again: a new ZIP code (40%), a nickname (10%), a
first or last name typo or a missing gender (5% each); 39 moved, 10 have a nickname, 8 a first
name typo, 2 a last name typo and 7 no gender. That makes 3,269 cardholders for 3,175 people, and
5,275 pharmacy claims (134 of them on the duplicate IDs). The duplicates come from their own
random generator, drawn after everything else, so they only add rows: every record and claim of
the Phase 7 feed is still in it, unchanged. A ground-truth file
records the member behind each cardholder, the variations and, for a duplicate, the first
cardholder ID; only `gold.identity_match_quality`, `gold.identity_dedupe_quality` and the
simulated reviewer read it.

**Methods.** Both compare first names after replacing known nicknames with the formal name (seed
`first_name_nicknames`, which covers the generator's nicknames, so its benefit here is an upper
bound).

- *Deterministic baseline* (`gold.identity_matches_deterministic`): a cardholder is linked when
  exact matches on first name, last name and birth date, or last name, birth date and ZIP code, or
  first name, birth date and ZIP code all point to one member.
- *Splink* (`gold.identity_matches_splink`, a dbt Python model): a Fellegi-Sunter model over first
  name (exact, nickname, three Jaro-Winkler levels), last name (with term frequency adjustments),
  birth date, gender and ZIP code, trained without labels (u from 2 million random pairs with a
  fixed seed, m by expectation maximisation). `gold.member_xref` links a cardholder automatically
  when the best candidate's match probability is at least 0.95, the first names do not disagree
  completely, no second candidate reaches 0.50 and no other PBM person claims the same member; a
  best candidate from 0.50 goes to review (`gold.identity_review_queue`), anything lower is
  unmatched.
- *Deduplication within the PBM* (`gold.identity_pbm_duplicates_splink`): the same comparisons,
  with Splink's `dedupe_only` link type on the cardholders alone. Its m probabilities come from the
  linkage of the PBM to the payer, trained the same way inside the model: the PBM's 94 true
  duplicate pairs are too few for expectation maximisation to observe every comparison level
  (a first model trained on them alone left three levels untrained, on Splink's default values).
  u and the prior come from the PBM's own random pairs. `gold.pbm_duplicate_pairs` merges a pair
  automatically from 0.95 when the first names do not disagree completely and the two cardholders
  do not have strong candidates that are different legacy members (the payer's records say they
  are two people); a pair from 0.50 that fails a condition goes to review, and so does a pair
  whose two cardholders have the same likely legacy candidate (from 0.50), whatever its own score:
  linking both to that member would make them one person. `gold.pbm_persons` groups the merged
  pairs into persons, and cardholder IDs of one person may link to the same member.

**Review.** The decisions of whoever works the queue live in a versioned dbt seed,
`identity_review_decisions` (review type, cardholder, candidate, `match` or `no_match`, reviewer,
date, note), and take precedence over the model: a `match` links the cardholder to the member the
reviewer chose, which may be any candidate the model scored, not only the best. `member_xref` and
`pbm_duplicate_pairs` keep the model's own decision (`model_status`) next to the final one and
record who decided. `gold.identity_review_audit` lists every decision and whether it still applies:
a decision applies while the model still proposes the case it decided, and a warning test
(`assert_identity_review_decisions_apply`) flags the ones the data made stale. The project has no
reviewers, so `scripts/review_identity_queue.py` (`make review`) stands in for them: it decides
each case from the ground truth, appends the decisions to the seed and repeats with a rebuild until
the queue is empty (a merged duplicate can change which member links compete; on this data the
first round decided all 183 cases and the second found none). Once the duplicate pairs are merged,
the model links the 50 cases queued because two PBM persons claimed the member on its own; their
decisions still apply. A reviewer who reads the truth is always right, so the figures after review
are an upper bound on what people would achieve. The seed holds 183 decisions, written from an
empty seed after the dedupe model changed (the change made 24 earlier decisions stale, which the
warning test reported):

## Reproducibility

The data generators and the gold models are pinned, so the results do not depend on the day they run:

- **Legacy source.** `generate_legacy_data.py` anchors every date to `--as-of` (default
  2026-09-28) instead of the current date, with a fixed seed (42). Pass `--as-of YYYY-MM-DD` to
  move the reference date.
- **Synthea.** `scripts/generate_synthea.sh` downloads a fixed release (`SYNTHEA_VERSION`,
  default `v4.0.0`, the latest stable release), checks the file's SHA-256 against the digest on
  the release page, and runs it with fixed seeds (`SEED`, `CLINICIAN_SEED`), a fixed reference
  date (`REFERENCE_DATE`, default `20260928`, Synthea's `-r` option) and a fixed end date
  (`END_DATE`, `-e`, default the reference date). Without `-e`, Synthea simulates up to the moment
  it runs, so a run on a later day adds encounters and observations. All are variables at the top
  of the script; changing the version also requires changing `SYNTHEA_SHA256`. Synthea also
  exports the organizations, locations, practitioners and practitioner roles its records
  reference (`scripts/synthea.properties`); turning that on left every other file unchanged.
- **PBM feed.** `scripts/generate_pbm_feed.py` reads the legacy members in a fixed order and uses
  its own random generator (seed 42 + 2) and the same reference date, so repeated runs write
  byte-identical files.
- **Identity resolution.** The Splink models sample their u probabilities with a fixed seed, run
  on one thread and sort their input by ID, so their scores are identical from build to build.
  The sort came with DuckLake, which does not keep a table's rows in a fixed order: without it,
  three builds gave three sets of scores (with the same decisions), because the random samples
  depend on the row order; with it, three builds gave identical scores. The review decisions are
  a versioned seed; `make review` dates them on the reference date, so the same data writes the
  same seed (started from an empty seed, it wrote the committed one byte for byte), and with the
  committed seed it finds an empty queue.
- **CI runner.** The workflow runs on `ubuntu-24.04`, not `ubuntu-latest`, which moves to a new
  release on its own.
- **Code systems.** The ICD-10-CM releases are pinned by URL and SHA-256. The FDA publishes only
  the current NDC Directory, so the NDC check uses the directory of the day it was downloaded
  (cached in `data/terminology/`; CI downloads it again each week); its date and SHA-256 are in
  `bronze.terminology_releases`. tx.fhir.org, used by `make fhir-validate-carin`, is also a live
  service whose content can change.
- **Gold models.** Wherever a model needs "today" (`fct_member_months`, and the
  `is_currently_covered` flag in `dim_member`), it uses the dbt variable `as_of_date` (default
  2026-09-28, the legacy generator's reference date) instead of `current_date`. Pass
  `--vars '{as_of_date: YYYY-MM-DD}'` to `dbt build` to move it, together with `--as-of`.

With the defaults, repeated runs produce the same legacy rows and the same Synthea resources, with
the same IDs and the same counts of each type. Two things in the Synthea output are not stable:
the order of lines within an NDJSON file, because Synthea writes its files in parallel, and a few
details of the allergy records. In repeated runs, a couple of the 1,710 CarePlans gained or lost a
duplicated "Allergy education" activity, and one of the 704 AllergyIntolerance resources had a
reaction severity present in one run and missing in another. No model or view reads these two
resource types, so none of the figures above depend on them.

Some figures still vary between runs: load times and CDC latency depend on the machine and on
timing, and the activity simulator (`make changes`) runs in real time without a fixed seed by
default.
