## The lakehouse: DuckLake

The three layers live in one [DuckLake](https://ducklake.select/) lakehouse, DuckDB's lakehouse
format. Its catalog (schemas, tables, snapshots, the list of data files and small inline writes)
is a Postgres database, the `lakehouse-catalog` service; its data is Parquet files under
`data/lakehouse/`, recorded in the catalog relative to that directory. `ingestion/lakehouse.py`
attaches it for every Python process, and dbt attaches it in `dbt/profiles.yml`; each passes its
own absolute path to `data/lakehouse/` (`OVERRIDE_DATA_PATH`), because the host, dbt and the
Airflow container see the repository at different places. `LAKEHOUSE_CATALOG` and
`LAKEHOUSE_DATA_PATH` change where they point.

- **Several writers.** Every process commits its transactions to the same catalog, so the CDC
  loader can write while dbt builds. DuckLake rejects only a conflicting commit (two writers
  changing the same table at the same moment); the loader retries a rejected batch on its next
  poll, as it would after any failed write.
- **What it is not.** DuckLake is not Apache Iceberg or Delta Lake. Its tables are Parquet files,
  but the metadata lives in its own catalog schema in Postgres, not in Iceberg or Delta metadata
  files, so engines that read those formats (Spark, Trino, Snowflake) cannot read these tables
  through it. Reading them takes DuckDB with the DuckLake extension.
- **Limits that shaped the code.** DuckLake has no primary key or unique constraints (keys are
  enforced by dbt tests and by the loaders), allows one `UPDATE` or `DELETE` per `MERGE` (the
  incremental models use delete+insert instead), and does not keep a table's rows in a fixed
  order (the Splink models sort their input, see Identity resolution).

Gold models: `dim_member`, `dim_plan`, `dim_provider`, `fct_claims`, `fct_pbm_claims`,
`fct_member_months`, `fct_prior_auth_timeliness`; the quality and reliability models
`dq_issue_summary`, `load_reliability`, `cdc_latency`, `cdc_slot_lag`, `fhir_view_parity` and
`terminology_code_check`; the identity resolution models (`identity_people`,
`identity_matches_deterministic`, `identity_matches_splink`, `identity_pbm_duplicates_splink`,
`pbm_duplicate_pairs`, `pbm_persons`, `member_xref`, `identity_review_queue`,
`identity_review_audit`, `identity_match_quality`, `identity_dedupe_quality`); the FHIR resources built from the
legacy and PBM data (`fhir_patient`, `fhir_coverage`, `fhir_explanation_of_benefit`,
`fhir_prior_authorization`, `fhir_organization`); and the SQL on FHIR view outputs (`vd_synthea__*`, `vd_legacy__*`).

## The simulated legacy source

`legacy_db/init/01_schema.sql` reproduces typical legacy traits: cryptic names, dates stored as
`VARCHAR(8)`, single-character codes and no foreign keys. The generator injects known issues at
documented rates (duplicate members, invalid gender codes, unparseable birth dates, claims for
unknown members, paid amounts above charges, orphan claim lines, claims with a service date
outside the member's coverage), so detection can be verified.

Claims also carry the fields the CARIN Blue Button profiles need: network status, type of bill and
revenue codes (institutional), place of service (professional), and NDC, days supply, dispense as
written code and refills (pharmacy), generated by `legacy_db/seed/claim_details.py` from a separate
random generator so that the other columns keep their values. Institutional claims spanning two or
more days are billed as inpatient. Provider NPIs have valid check digits.

`legacy_db/seed/simulate_changes.py` generates day-to-day activity, one transaction per event:
prior authorization decisions and new requests, claim adjudication, new claims, member address
changes and deletion of voided claims.

## Change data capture

`ingestion/cdc_legacy.py` reads the legacy database's write-ahead log through a logical
replication slot (wal2json). It does not change the legacy tables and it captures deletes.

- **Initial snapshot.** The slot is created before the tables are copied, so no change committed
  during the copy is lost. Changes that are both in the copy and in the slot are replayed on top of
  the copied rows; each change carries the full new row, so the final state is the same.
- **Bronze change tables.** Each legacy table has an append-only `bronze.legacy_<table>_changes`
  table: one row per change (`_op` = S snapshot, I insert, U update, D delete, T truncate), with the
  log position (`_lsn`, plus `_seq` for rows that a bulk write such as `COPY` puts in one WAL record),
  the source commit time (`_commit_ts`) and the arrival time (`_loaded_at`).
- **No lost or repeated batches.** Changes are read without being consumed (`peek`), written to
  the lakehouse in one transaction together with the last commit LSN (`bronze._cdc_state`), and only then
  released from the slot (`advance`). If the loader stops between the two steps, the next run skips
  the batch that was already stored. A dbt test checks that no log position (`_lsn`, `_seq`) appears
  twice.
- **Current state, incremental.** Each legacy table has an incremental model,
  `silver.cdc_current__<table>` (macro `cdc_current_state`), with the latest version of each
  primary key. The first build takes every change after the last TRUNCATE. After that, a run
  reads only the changes past its watermark, the highest `_lsn` in the table, takes the latest per
  key (rows that share an `_lsn` ordered by `_seq`) and merges them by key (delete+insert). A key
  whose latest change is a delete stays as a tombstone (`_op = 'D'`), so the watermark is always
  the last change applied; the `stg_legacy__*` views filter tombstones out. The model rebuilds
  itself when the history no longer continues from it: a TRUNCATE past the watermark, or a new
  snapshot (each row records the snapshot it came from, `_snapshot_lsn`, which also catches a
  recreated source database whose log positions start again).
- **Two checks of the current state.** `assert_cdc_current_state_matches_full` compares each
  incremental table with a full rebuild from all its changes (the `legacy_current_state` macro),
  up to the incremental table's watermark, so changes the loader appends while dbt runs do not
  count against it. `scripts/cdc_reconcile.py` (`make cdc-reconcile`) compares it with the
  Postgres tables, row by row. `make cdc-check` runs the whole path: simulated changes, a sync, the
  incremental build, both checks; CI runs it last.
- **Slot monitoring.** A replication slot makes Postgres keep WAL until it is consumed, so a
  stopped loader makes the database log grow. Three pieces handle that:
  - *A cap.* The legacy database sets `max_slot_wal_keep_size = 1GB` (`docker-compose.yml`). Past
    it, Postgres invalidates the slot (`wal_status = lost`) instead of filling the disk.
  - *An alert that does not depend on the loader.* `make slot-check`
    (`cdc_legacy.py slot-status`) reads `pg_replication_slots` and fails when the slot holds more
    than 512 MB of WAL (half the cap), when it is beyond the cap (`unreserved`), when it was lost,
    or when it does not exist. It reads only Postgres, so it works when the loader or the lakehouse
    is stuck, which is when the lag grows; the `cdc_slot_monitor` DAG runs it every 5 minutes.
  - *History and recovery.* Before each sync the loader records the slot state in
    `bronze._cdc_slot_status`, and `gold.cdc_slot_lag` summarizes it (WAL retained and pending, the
    longest gap between syncs, slot losses). When the loader finds the slot lost, it records the
    loss and takes a new snapshot, since the WAL it had not read is gone. The new snapshot replaces
    the change tables, so the CDC latency history starts over. A dbt test warns when a loss is in
    the history.

  `make slot-drill` proves the chain: with the loader stopped, it writes WAL until the slot is
  lost and checks the alert, the loss and the recovery. CI runs it on every pull request. To
  release the slot by hand, run `python ingestion/cdc_legacy.py drop-slot`; the next
  `make ingest` takes a new snapshot.

## Orchestration

`airflow/dags/payer_lakehouse.py` defines three DAGs, run by Airflow 3 in Docker
(`make airflow-up`, UI at http://localhost:8080, no login in this local setup):

| DAG                      | Schedule          | Tasks                                                   |
|--------------------------|-------------------|---------------------------------------------------------|
| `legacy_cdc_refresh`     | every 30 minutes  | `cdc_sync` → `dbt_build`                                |
| `lakehouse_full_refresh` | manual            | `cdc_sync` → `load_fhir` → `load_pbm` → `load_terminology` → `views_check` → `dbt_build` → `dbt_coverage` |
| `cdc_slot_monitor`       | every 5 minutes   | `slot_check` (fails when the replication slot needs attention) |

All DAGs start paused. Design choices:

- **Airflow only orchestrates.** Tasks call the same scripts and `dbt build` used by `make`,
  through `BashOperator`. The loaders and dbt run in their own virtualenv inside the image, so
  their dependencies never conflict with Airflow's. Versions are pinned in `requirements.txt`,
  because the host and the container write the same lakehouse with the same DuckDB (and DuckLake
  extension) version.
- **dbt builds one at a time.** Until the move to DuckLake, every task that wrote the lakehouse
  queued in the `lakehouse` pool, because a DuckDB file allows one writer. Now the loaders run
  whenever their DAG reaches them, and only `dbt_build` stays in the pool (one slot): two builds
  rewrite the same tables, and DuckLake would reject one of them. `slot_check` reads only
  Postgres, so a stuck lakehouse cannot delay the alert. A `make dbt` on the host while Airflow
  builds would be the same kind of conflict.
- **Failure policy.** Each task retries twice, except `slot_check`, whose failed run is the
  alert and should show at once. Data tests configured as warnings (known legacy issues) do not
  fail `dbt_build`; test errors do.
- **Local setup.** `airflow standalone` with the LocalExecutor and a separate Postgres for Airflow
  metadata. A production deployment would run the scheduler, API server and workers as separate
  services with real authentication.

## SQL on FHIR

`fhir/sof_duckdb/` compiles [SQL on FHIR v2](https://sql-on-fhir.org/) `ViewDefinition`s into DuckDB
SQL, so the views run inside the lakehouse on the raw FHIR JSON in bronze.

- **How it compiles.** Every FHIRPath expression becomes a DuckDB expression of type `JSON[]` (a
  FHIRPath collection). Each `select` becomes a list of JSON rows: `forEach` maps over a collection,
  `unionAll` concatenates lists and nested selects are combined with a cartesian product. The query
  then unnests the rows of each resource and projects the columns. Everything is an expression over
  the resource, with no joins, because DuckDB does not allow subqueries inside lambdas.
- **Conformance.** `make conformance` runs the specification's shared test suite
  ([sql-on-fhir.js](https://github.com/FHIR/sql-on-fhir.js), pinned to commit `0821b67`) and
  compares results the way the reference runner does. Not supported: `lowBoundary()` and
  `highBoundary()` (experimental). `repeat` is unrolled to 10 levels.
- **dbt integration.** `make views` turns each file in `fhir/view_definitions/` into a dbt macro that
  takes the relation holding the resources, so one view runs over any source:
  `select * from {{ vd_eob_summary(ref('fhir_explanation_of_benefit')) }}`. The generated macros are
  committed; Airflow's `views_check` task fails if they are out of date.

Four views are defined: `patient_demographics`, `coverage_summary`, `eob_summary` and `eob_items`.

## Legacy data as FHIR

The gold models `fhir_patient`, `fhir_coverage`, `fhir_explanation_of_benefit` and
`fhir_organization` turn the legacy warehouse into FHIR R4 resources that conform to the
[CARIN Blue Button](https://hl7.org/fhir/us/carin-bb/) profiles (STU 2.1.0), an implementation
guide CMS recommends for the Patient Access API. Each resource declares its profile in
`meta.profile`; an ExplanationOfBenefit gets the Professional-NonClinician, Inpatient-Institutional,
Outpatient-Institutional or Pharmacy profile from its claim type and type of bill. The payer and the
providers (clinics) are Organization resources that the other resources reference.

Prior authorizations follow the [Da Vinci PDex](https://hl7.org/fhir/us/davinci-pdex/) Prior
Authorization profile (STU 2.1.0; CMS lists 2.0.0 and 2.1.0 for the Patient Access API, the
first as derived from expired standards). `fhir_prior_authorization` builds an
ExplanationOfBenefit with `use = preauthorization` per legacy request: the requested CPT code as
the item, the decision as a review action on its adjudication (X12 306: A1 approved, A3 denied, A4
pending), the decision time as `base-ext-when-adjudicated`, the requested amount as the
`submitted` adjudication PDex requires there, the urgency as `priority` (stat or normal) and
`outcome` queued while pending. PDex points the Coverage to Da Vinci HRex and the other references
to US Core, which adds two requirements the claims did not have: an identifier on the payer
Organization, and a birth date on the Patient, so a birth date the legacy source has invalid is
exported as a data-absent reason (`unknown`) instead of being left out.

- **Narrative and plan type.** Every resource carries a generated narrative (`text`, macro
  `fhir_narrative`) built from its own data, and each Coverage the plan's Source of Payment
  Typology code (the Payer Type value set CARIN binds). An NPI is typed `NPI`, as CARIN requires,
  and `PRN`, the base FHIR code that fits it.
- **Nothing invented.** Legacy gender codes outside M/F/U become `unknown`, which the profile
  requires in place of an omitted gender and which states that the value is not known; the invalid
  source codes stay counted in `gold.dq_issue_summary`. Invalid NPIs would be left out of the
  Organization identifier. FHIR's rule against null values and empty arrays is enforced when the JSON
  is built.
- **Integrity gate.** An ExplanationOfBenefit requires a patient and a coverage, so claims with an
  unknown member or outside the member's coverage are not exported; they stay flagged in
  `gold.fct_claims`.
- **Round trips.** `gold.fhir_view_parity` runs the ViewDefinitions over the legacy-derived
  resources and compares the result with the gold tables they came from, row by row. It also
  compares the `patient_demographics` view over Synthea with the hand-written `stg_fhir__patients`.
  A dbt test fails if any comparison finds a row on only one side.
- **References.** A dbt test (`assert_fhir_references_resolve`) checks that every reference in the
  exported resources points to an exported resource.
- **Validation.** `make fhir-validate-carin` runs the official HL7 FHIR validator (6.10.4) against
  the CARIN Blue Button 2.1.0 package on a reproducible sample: 200 resources per resource type and
  per ExplanationOfBenefit profile, each in a Bundle with the resources it references, so references
  resolve and referenced resources are checked against their target profiles. CI runs it on every
  pull request, with tx.fhir.org as the terminology server, so codes are checked too. `make
  fhir-validate` checks the same kind of sample against base FHIR R4 only, without a terminology
  server (`-tx n/a`). Codes from code systems the server does not have (NUBC revenue codes, the
  NCPDP dispense as written code) are counted as unverified instead of failing the run. Two
  warnings the data cannot remove are counted apart as known warnings, each with its reason
  (`KNOWN_WARNINGS` in `fhir/validate.py`): the identifier types CARIN requires (`uc`, `MB`), which
  the base value set lacks, and tx.fhir.org's NDC, a 2021 snapshot that marks every code inactive.
- **PDex validation.** `make fhir-validate-pdex` validates one sample per decision (approved,
  denied, pending) against the PDex 2.1.0 package, in Bundles as above, so the Coverage is checked
  against HRex and the Patient and Organizations against US Core. The X12 review action codes are
  counted as unverified: X12 code lists are licensed.
- **Terminology, on every resource.** The validator sees a sample. `ingestion/load_terminology.py`
  loads the public code lists into bronze: the CMS ICD-10-CM releases for FY2021 to FY2026 (pinned
  by SHA-256) and the FDA NDC Directory (only the current one exists; its date and SHA-256 are
  recorded); the CMS place of service codes are a seed. `gold.terminology_code_check` reads every
  code in the exported ExplanationOfBenefit resources through a ViewDefinition (`eob_codes`) and
  checks it on the service date: an ICD-10-CM code must be billable in that fiscal year's release,
  and an NDC listed and marketed. Licensed code systems (CPT, NUBC) and the NCPDP stub are
  reported as unverified. `assert_terminology_codes_valid` fails the build on an invalid code.

## The FHIR API

A HAPI FHIR server (`hapiproject/hapi:v8.12.0-2`, service `fhir-server`, profile `api` in
`docker-compose.yml`) serves the gold resources at `http://localhost:8090/fhir`. Its H2 database
lives inside the container, and `make fhir-up` recreates the container, so every load starts from
an empty server and a resource removed from gold cannot linger. The server does not validate
requests: the resources are validated before they are published.

- **Publish.** `fhir/publish.py` (`make fhir-publish`) first loads the five search parameters that
  CARIN Blue Button and PDex require of a server and base FHIR R4 lacks (ExplanationOfBenefit
  `type`, `service-date`, `service-start-date`, `billable-period-start` and `use`, copied from
  the two packages into `fhir/server/search_parameters/`), so the data is indexed with them. Then
  it loads Organization, Patient, Coverage and ExplanationOfBenefit (claims, then prior
  authorizations) from the gold models, in that order, as transactions of 500 PUTs by ID: a batch
  loads completely or not at all, and a second run replaces instead of duplicating.
- **Check.** `fhir/api_check.py` (`make fhir-api-check`) computes every expected figure from gold
  and compares it with the server: the count of each resource type and of ExplanationOfBenefit by
  `use` and `type`; the searches the CARIN and PDex capability statements require (by patient,
  identifier, use, billable period), on a reproducible sample of members, claims and PBM cardholder
  IDs; and a system-level Bulk `$export`, whose IDs must be exactly the gold IDs and whose
  resources must equal gold apart from `meta`. Searches are sent with `Cache-Control: no-cache`,
  because HAPI reuses the result of an identical search for a minute.
- **What the server changes.** HAPI sets `meta.versionId` and replaces `meta.lastUpdated` with the
  time it stored the resource. The legacy update time stays in gold. Since every publish loads
  every resource, `_lastUpdated` on the server is the publish time; a production feed would publish
  only the resources that changed.
- **Orchestration.** Publishing is a `make` step, run in CI after the validations; the Airflow DAGs
  do not publish, so after a refresh in Airflow the server is updated with `make fhir-publish`.

## The PBM feed and identity resolution

A second source sends the same people under different identifiers. A pharmacy benefit manager
(PBM) administers the pharmacy benefit for part of the members, issues its own cardholder IDs and
sends pipe-delimited files: cardholders, pharmacies and pharmacy claims.
`scripts/generate_pbm_feed.py` (`make pbm`) builds them from the legacy members, with nicknames,
typos, changed last names, transposed or mistyped birth dates, old addresses and missing fields at
documented rates, plus people the payer does not know, including look-alikes. A ground-truth file
records who is who. `ingestion/load_pbm.py` loads the files into bronze as text, like any file
feed, and staging types them (`stg_pbm__*`).

Identity resolution happens in the data layer, before anything reaches the API:

- **One shape.** `identity_people` puts both sources in the same normalized form (names lower case,
  letters only; a nickname also mapped to the formal name through the seed `first_name_nicknames`).
- **Baseline.** `identity_matches_deterministic` links on exact rules, the way a first master
  patient index often does.
- **Probabilistic model.** `identity_matches_splink` is a dbt Python model that runs
  [Splink](https://moj-analytical-services.github.io/splink/) (Fellegi-Sunter) on an in-memory
  DuckDB with one thread and its input sorted by ID, so its working tables stay out of the
  lakehouse and its scores are the same on every run (the random samples depend on the row order,
  which the lakehouse does not fix). It is trained without labels.
- **Deduplication within the PBM.** A PBM can reissue a card and key the same person again.
  `identity_pbm_duplicates_splink` runs the same comparisons with Splink's `dedupe_only` link type
  on the cardholders alone. Its m probabilities come from the PBM-to-payer linkage, trained the
  same way inside the model, because the PBM's own duplicates are too few to train every
  comparison level; u and the prior come from the PBM's random pairs. `pbm_duplicate_pairs` merges
  a pair automatically only when the match is strong, the first names do not disagree completely
  and the payer's records do not say they are two different members; a pair whose cardholders
  share a likely legacy candidate goes to review whatever its own score. `pbm_persons` groups
  merged pairs into persons.
- **Decisions.** `member_xref` links a cardholder automatically only when the match is strong, the
  first names do not disagree completely (relatives such as twins share last name, birth date and
  address), there is no second likely candidate and no other PBM person claims the member (the
  cardholder IDs of one person may share a member). Likely matches and likely duplicates that fail a
  condition go to `identity_review_queue`, with both records side by side, instead of being merged.
  Thresholds are dbt variables (`identity_auto_link_probability`, `identity_review_probability`).
- **Review.** Reviewers' decisions are a versioned dbt seed, `identity_review_decisions`, applied
  over the model: a `match` can pick any scored candidate, a `no_match` keeps the records apart.
  `member_xref` and `pbm_duplicate_pairs` keep the model's own decision next to the final one and
  record who decided. `identity_review_audit` shows whether each decision still applies (the model
  must still propose the case it decided); stale ones raise a warning test and the case returns to
  the queue. `scripts/review_identity_queue.py` (`make review`) simulates a reviewer from the ground
  truth, so its results are an upper bound.
- **Measurement.** `identity_match_quality` compares the methods with the ground truth, overall and
  by variation, before and after review; `identity_dedupe_quality` does the same for duplicates.
  They and the simulated reviewer are the only readers of the truth. `assert_identity_match_quality`
  fails the build if an automatic link is wrong or recall falls below 95%, or if a link is wrong
  after review; `assert_identity_dedupe_quality` fails on a wrong merge, and
  `assert_member_linked_to_one_person` if two PBM persons share a member.
- **FHIR.** A linked member's Patient carries each of the person's PBM cardholder IDs as a member identifier.
  PBM claims of linked members with coverage on the fill date become ExplanationOfBenefit
  resources (Pharmacy profile) that reference the member's Patient and Coverage and the pharmacy's
  Organization; the view parity and the CARIN validation cover them as a separate sample. Claims
  of cardholders in review or unmatched stay in `fct_pbm_claims`, flagged.
